# element-skin Webhook 实际应用测试方案（定稿）

> 版本：v3（定稿） · 日期：2026-08-19
> 关联契约文档：`element-skin/doc/Webhook设计与开发者契约.md`

## 1. 测试目标

在真实公网部署下，用两个实际应用验证 element-skin Webhook 的完整契约，并产出性能报告：

1. **应用 A（PlayerWall）**：验证用户委托路径的真实业务——事件通知 + API 拉状态 + 授权撤销即下架；
2. **应用 B（Webhook Probe）**：验证机密应用 app-only 管理事件路径；
3. 覆盖全部 15 种事件类型、签名/重试/幂等/授权重检/SSRF 防护等可靠性契约；
4. 产出端到端延迟、吞吐与 worker 资源预算的性能报告。

## 2. 部署架构

### 2.1 云服务器（Debian 系，2C2G 轻量，有域名 + TLS）

```
┌────────────────────────── 云服务器 ──────────────────────────┐
│                                                             │
│  Nginx (443, TLS)                                           │
│   ├─ skin.your-domain.com  → element-skin demo 前端          │
│   │      /skinapi/ 反代 → backend:8000                      │
│   └─ hooks.your-domain.com → FastAPI 接收端 (127.0.0.1:8080) │
│                                                             │
│  Docker Compose: db(postgres) + redis + backend + webhook-worker │
│  Systemd: element-skin-receiver（接收端，独立进程）             │
│                                                             │
│  webhook endpoint URL = https://hooks.your-domain.com/...   │
│  （公网域名解析到服务器公网 IP → 满足 SSRF 防护 → Nginx 回环）   │
└─────────────────────────────────────────────────────────────┘
```

**关键点**：demo 站与接收端同机，但 endpoint 必须用公网域名（SSRF 强制公网 IP + HTTPS），连接经公网 IP 回环到 Nginx——恰好真实验证 SSRF 防护。

### 2.2 本地（Windows，开发侧）

- 开发/调试用：`go run ./cmd/element-skin` + `go run ./cmd/webhook-worker` + `npm run dev`；
- 所有测试脚本本地编写，通过云服务器 API 驱动；
- 可选：本地再起一份 element-skin，做**跨网投递**对比（本地→云端接收端），与同机回环对比，量化公网网络开销。

## 3. 应用设计

### 3.1 应用 A：PlayerWall（公开应用，用户委托）

**定位**：Minecraft 社区官网的玩家皮肤墙组件。成员授权后，角色与皮肤实时展示；撤销授权即下架（隐私保护闭环）。

| 项 | 值 |
| --- | --- |
| 类型 | public（Authorization Code + PKCE） |
| 权限 | `profile.read.owned`、`texture.read.owned`、`oauth_grant.read.owned` |
| 订阅事件 | `profile.created/updated/deleted`、`texture.created/updated/deleted`、`oauth_grant.revoked` |
| 回调 | `/callback`（OAuth 授权码回调，存 refresh token） |

**业务处理逻辑**（接收端后台 worker，按 `event.id` 幂等处理）：

| 事件 | 处理 |
| --- | --- |
| `profile.created` | 回查 `/v2/users/me/profiles` → 建角色卡片（名字、UUID、纹理模型） |
| `profile.updated` | 回查最新资料 → 更新卡片（改名/模型变更） |
| `profile.deleted` | 直接下架卡片（**资源可能已不存在**，回查 404 也要正确处理） |
| `texture.created/updated` | 更新卡片引用的皮肤/披风 URL（不下载文件） |
| `texture.deleted` | 清空对应纹理引用 |
| `oauth_grant.revoked` | **下架该用户全部角色卡片**（授权终止 = 数据移除） |

**对外界面**：
- `GET /`：公开皮肤墙（角色卡片墙，可嵌入官网 iframe）；
- `GET /api/players`、`GET /api/players/{uuid}`：公开 API（供论坛/Discord 集成）；
- `GET /admin/status`：接入玩家数、同步状态、失败重试、最近事件。

### 3.2 应用 B：Webhook Probe（机密应用，app-only）

**定位**：测试探针，覆盖 A 不涉及的管理型事件路径。

| 项 | 值 |
| --- | --- |
| 类型 | confidential（Client Credentials，app-only） |
| 权限 | `permission.read.any`、`account.read.any`、`official_whitelist.read.any`、`oauth_grant.read.owned` |
| 订阅事件 | `permission.updated`、`account.created/deleted`、`official_whitelist.added/removed`、`oauth_grant.*` |
| 特殊 | 独立 endpoint + 独立 `signing_secret`，`/probe/*` 故障注入路径 |

### 3.3 事件覆盖矩阵（全部 15 种）

| 路径 | 应用 | 事件 |
| --- | --- | --- |
| 用户委托 | A | `profile.*`（3）、`texture.*`（3）、`oauth_grant.revoked`（定向） |
| app-only | B | `permission.updated`、`account.created/deleted`、`official_whitelist.added/removed`（5） |
| 定向 | B | `oauth_grant.created/updated/revoked`（3） |

> B 也订阅 `oauth_grant.*`，用于验证「grant 只投递给所属应用」的定向语义（A 收不到 B 的 grant 事件）。

## 4. 接收端设计（`receiver/`）

```
receiver/
├── app.py                 # FastAPI 主应用：两个 endpoint + 业务处理 + 面板
├── replay_guard.py        # 持久化 ReplayGuard（sqlite3，Webhook-Id 唯一索引原子 claim）
├── verifier.py            # 封装 python-sdk WebhookVerifier（按 endpoint 分密钥）
├── worker.py              # 后台线程：从 inbox 取事件 → 幂等业务处理 → 记录结果
├── playerwall.py          # 应用 A 业务：卡片 CRUD + 公开 API
├── probe.py               # 应用 B 业务：事件记录 + 故障注入控制
├── config.py              # signing_secret、站点 API base、token 管理
├── requirements.txt
└── tests/                 # 接收端自测（对拍签名、幂等、业务规则）
```

**关键实现要求**：
- 验签用 `python-sdk` 的 `WebhookVerifier`（原始 body、恒定时间比较、5 分钟容差、64KiB 上限）；
- ReplayGuard 用 SQLite 持久化：`claim(event.id, delivery_id)` 原子插入，重复返回 False → 204；
- 业务处理用**独立后台线程池**，不在 HTTP 请求内做慢操作（契约纪律）；
- 收到 `2xx` 后立刻返回，业务异步完成；
- 所有事件、验签结果、处理结果落库，供面板和报告统计。

## 5. 测试驱动脚本（`scripts/`）

```
scripts/
├── create_apps.py     # 通过 /v2/oauth/apps 创建 A/B、提交审核、管理员激活、读 signing_secret
├── authorize_a.py     # 应用 A 授权码 + PKCE 全流程（浏览器自动化或手动，存 refresh token）
├── drive_events.py    # 触发事件：注册用户/建角色/改名/删角色/传皮肤/删皮肤/改权限/白名单
├── fault_tests.py     # 可靠性用例（重试/幂等/验签失败/撤销/越权/非 HTTPS）
└── perf.py            # 性能测试（批量事件、延迟/吞吐统计）
```

**事件触发 API 映射**（从 `element-skin/skin-backend/internal/httpapi/routes.go` 核实）：

| 事件 | 触发 API |
| --- | --- |
| `account.created` | `POST /v2/auth/register` |
| `profile.*` | `POST/PATCH/DELETE /v2/users/me/profiles...` |
| `texture.created` | `POST /v2/users/me/textures`（multipart 上传） |
| `oauth_grant.*` | 授权流程 / `DELETE /v2/oauth/grants/{grant_id}` |
| `permission.updated` | `PUT/DELETE /v2/admin/users/{id}/permissions/{code}` 或角色 `PUT/DELETE /v2/admin/users/{id}/roles/{role_id}` |
| `official_whitelist.*` | `POST/DELETE /v2/admin/official-whitelist` |

## 6. 测试用例矩阵

### 6.1 应用 A · PlayerWall 业务链路

| # | 用例 | 期望 |
| --- | --- | --- |
| A1 | 玩家注册 + 授权 A → 皮肤墙出现空状态 | 无卡片，授权成功 |
| A2 | 创建角色 → `profile.created` → 卡片出现 | 卡片含名字 + UUID |
| A3 | 改名 → `profile.updated` → 卡片更新 | 名字变化，`event.id` 不同，卡片不重复 |
| A4 | 上传皮肤 → `texture.created` → 卡片纹理 URL 更新 | 引用 URL 正确 |
| A5 | 换肤 → `texture.updated` | 纹理 URL 变化 |
| A6 | 删皮肤 → `texture.deleted` | 纹理引用清空 |
| A7 | 删角色 → `profile.deleted` → 卡片下架 | 回查 API 404 仍正确处理 |
| A8 | 撤销授权 → `oauth_grant.revoked` → 全部下架 | 隐私闭环 |
| A9 | 重复投递（重试）→ 卡片不重复 | `event.id` 幂等 |

### 6.2 应用 B · Probe 边界路径

| # | 用例 | 期望 |
| --- | --- | --- |
| B1 | 改用户权限覆盖 → `permission.updated` 到达 | app-only 无 grant 也投递 |
| B2 | 加/删角色 → `permission.updated` 再次到达 | 同上 |
| B3 | 注册新用户 → `account.created` | 到达 |
| B4 | 删除用户 → `account.deleted` | 到达 |
| B5 | 加/删官方白名单 → `official_whitelist.*` | 到达 |
| B6 | 用户授权/撤销 B → 收到 `oauth_grant.*` 三件套 | 定向投递（A 收不到 B 的 grant 事件） |
| B7 | 管理员事件改 grant 拥有者权限 → 撤销后停止投递 | 授权重检 markDead |

### 6.3 可靠性 & 安全

| # | 用例 | 期望 |
| --- | --- | --- |
| C1 | 接收端返回 500 → 指数退避重试 | 首约 30s，12 次/72h 上限，最终 dead |
| C2 | 接收端 >10s 不响应 → 超时重试 | 同上 |
| C3 | 手动重放同 `Webhook-Id` | 204，inbox 无重复 |
| C4 | 篡改 body / 伪造签名 / 过期时间戳 | 400，验签失败记录 |
| C5 | 事件产生后、投递前撤销 grant | worker 重检后不再外发（markDead） |
| C6 | endpoint 选未申请权限事件 | 创建/更新 400 |
| C7 | endpoint 配 http:// 或私网 IP | 400（SSRF 防护） |
| C8 | endpoint 停用 → 恢复 | 停用期间不投递 |
| C9 | 时钟偏差 >5 分钟 | 400 |

## 7. 性能测试设计

与现有 `element-skin/reports/webhook-load-test.md` 口径一致，但用真实公网链路：

### 7.1 场景

| 场景 | 方法 | 指标 |
| --- | --- | --- |
| 端到端延迟 | 批量创建 1000 个角色（脚本并发触发），记录每个事件从 API 请求发出到接收端 204 的时间 | P50/P95/P99 |
| 吞吐 | 固定 1000 事件，测 worker 完成投递的总耗时 | events/min、events/s |
| 网络开销 | 同机回环 vs 本地→云端跨网投递 | 延迟差值（公网开销） |
| 资源预算 | 默认预算（2 连接/3000ms）vs 调参（如 4 连接/1000ms） | 吞吐提升、主站请求延迟影响 |
| SQL 效率 | 抽查 worker 批次 SQL 次数 | 对比 0.08 次/event 基准 |

### 7.2 报告结构（`report/webhook-real-deployment-test.md`）

1. 测试环境（服务器规格、版本、网络拓扑）；
2. 应用与配置（A/B 的应用 ID、权限、endpoint、密钥管理）；
3. 功能测试结果表（6.1/6.2/6.3 全用例）；
4. 性能数据（延迟分布表、吞吐曲线、预算对比）；
5. 发现的问题与结论（含对 worker 预算建议的验证）；
6. 附录：原始数据、复现命令。

## 8. 风险与约束

| 风险 | 应对 |
| --- | --- |
| 2C2G 跑 demo + 接收端 + 压测，资源紧张 | 压测错峰；worker 默认 2 连接保护主站；性能测试用本地实例做吞吐，云端做真实链路延迟 |
| demo 站与接收端同机的回环投递不代表跨网 | 增加本地→云端跨网对比场景 |
| 测试污染 demo 数据 | 用独立测试账号（`webhook-*@test.com`），结束后清理 |
| 邀请码注册限制 | 用管理员 API 生成邀请码或直接调注册 API（若关闭注册限制则直接注册） |
| `oauth_grant.revoked` 需真实授权 | A 走完整 PKCE 授权；B 用 Client Credentials 之外再用一次用户授权补 grant 三件套 |
